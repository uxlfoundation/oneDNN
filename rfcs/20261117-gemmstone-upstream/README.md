# Make oneDNN the Upstream for gemmstone

## Introduction

gemmstone is the JIT GEMM generator for Intel GPUs. oneDNN uses it for
matmul, inner product, RNN and SDPA. The primary copy of gemmstone is in an
Intel-internal repository. oneDNN keeps a hand-synced copy in
`src/gpu/intel/gemm/jit/`.

### Motivation

The internal repository is primary only in name. Most gemmstone development
happens in oneDNN, and the internal repository gets oneDNN changes only
through periodic batch backports. Statistics for 2025-11-17 to 2026-11-17:

- **Internal repository**: 152 merged PRs. 97 track oneDNN: 41 ports, 29
  upstreaming prep and 27 DSL PRs done in lockstep with oneDNN. About 45 are
  tools, build or docs. Only 9 are independent generator changes.
- **oneDNN**: about 345 PRs touched gemmstone (239 on main, 106 on internal
  development branches). Only 2 were syncs from the internal repository,
  about 150 lines in total. CRI enabling alone took 49 oneDNN PRs and 7
  internal ones.

Backports lag, and some fixes never reach the internal repository. The
internal repository has no CI that runs oneDNN tests across GPUs. Thus, its
changes are fully tested only after they are ported to oneDNN. The primary
copy must be where development and validation already happen.

## Proposal

1. Make oneDNN the single upstream. Move gemmstone to
   `src/gpu/intel/gemmstone/`. The oneDNN glue (`pd.*`, `gen_kernel*`) stays
   in `src/gpu/intel/gemm/jit/`. Remove the `ONEDNN_GEMMSTONE_DIR` CMake
   option: oneDNN always uses its own copy.
2. Add a standalone CMake build in `src/gpu/intel/gemmstone/`. It does not
   depend on oneDNN and uses nGEN from `third_party/ngen`. In the oneDNN
   build, `src/gpu/intel/jit/config/gemmstone_config.hpp` injects oneDNN's
   post-ops, generator base class, verbose and serialization. The standalone
   build has no post-op support. Standalone-only code is under
   `GEMMSTONE_STANDALONE` and is not compiled in the oneDNN build, so
   kernels generated by oneDNN do not change. Earlier PRs (#6021, #6182,
   #6274, #6441) already aligned the oneDNN copy with the internal one.
3. Move the tools (`frontend`, `benchstone`, `ktool`, `multiderby`,
   `pvc_derby`), unit tests and documentation. The oneDNN library build does
   not build them.
4. Enable the existing job in oneDNN internal CI that builds gemmstone
   standalone, including the tools, and runs its unit tests. The unit tests
   check only kernel generation, so they run on CPU and need no GPU.
5. Archive the internal repository. It gets no more changes and no sync.

### Why the tools move too

`ktool` (catalog management, kernel ranking, model fitting) and `multiderby`
(autotuner) depend on gemmstone internals: the strategy parser, catalog
structures, evaluator and generator. Changes to these often need a tool
change. In a separate repository, no CI builds the tools against oneDNN
changes, so they break unnoticed. That CI must also track the public code and
the embargoed (not yet public hardware) code. In the oneDNN tree, the
standalone CI job builds the tools against the same sources. External
contributors also gain catalog tuning.

The best long-term state is a decoupled tool layer with a stable interface,
possibly in its own repository. That needs interface design work. The sync
problem needs a fix now, so the tools stay in the same tree for now.

### Impact

No API, ABI or performance change. The library build gets no new
dependencies. The standalone build needs C++20 and OpenCL; MKL is optional.
The tree grows by about 35k lines (tools 29k, docs, tests and CMake 4k,
standalone-only generator code 2k).

## Alternatives

- **Status quo (manual sync)**: drift and lost fixes continue, each change
  needs two PRs, and internal changes stay untested until ported.
- **Git submodule**: each change needs a gemmstone PR and then a submodule
  bump in oneDNN. Development branches must be paired. Embargoed work needs a
  second internal gemmstone fork, in addition to the internal oneDNN one.
- **Independent project with its own CI**: gives clean boundaries, but needs
  a second CI with the same capabilities and dedicated owners. Development is
  in lockstep with oneDNN, so cross-repository sync remains.

## Status

A branch that moves gemmstone, adds the standalone build and brings the tools,
tests and docs is ready. The standalone CI job exists and only needs enabling.
